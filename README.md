# LARCH 编译器

面向 **LARCH / LSL 规格语言** 的桌面编辑器与静态分析工具：Java Swing 界面 + 自研词法分析、语法分析、
等式检查（规格验证）。可以在一个窗口里编写 `.lsl` 规格、查看 token 流与语法树、检查断言等式的成立情况。

> 课程设计项目改造而来，未声明开源许可。

---

## 一、功能

| 能力 | 状态 | 说明 |
|---|---|---|
| 多标签编辑、行号、关闭确认 | ✅ | `JCloseableTabbedPane` + `TextLineNumber` |
| 撤销 / 重做 / 复制 / 剪切 / 粘贴 / 全选 / 查找 | ✅ | 基于 `UndoManager` |
| 字体设置、光标行列状态栏、项目文件树 | ✅ | `JFontDialog` / `JStatusBar` / `JFileTree` |
| **词法分析** | ✅ | token 表（类型/词素/行/列，可排序），错误进「错误列表」 |
| **语法分析** | ✅ | 递归下降生成 AST，渲染为缩进语法树 |
| **规格检查（运行 F5）** | ✅ | 验证 asserts 定义自洽、implies 推论成立，给出「自洽 / 矛盾 / 无法验证」判决 |
| 错误列表 | ✅ | 词法、语法错误均带行列定位，出错自动切换页签 |
| 语法高亮 | ❌ | `CodeStyle` 的关键字表仍未启用 |

一个文件可包含多个 trait，界面会依次渲染、逐 trait 检查。

## 二、快速开始

**环境要求**：JDK 17 及以上（开发验证于 JDK 21）。**无需预装 Maven**，项目自带 Wrapper。

```powershell
.\mvnw.cmd package          # 编译 + 测试 + 打包
java -jar target\LarchCompiler.jar
```

首次构建会通过 Wrapper 下载 Maven 与依赖。

VS Code 中按 `Ctrl+Shift+B` 执行默认任务（`Larch: package (jar)`），另有 `compile` / `test` / `run` / `clean`。

## 三、使用

1. 打开 `src\main\resources\samples\` 下的样例（文件对话框选「所有文件」）
2. 点 **词法分析** → 右侧「词法分析」页显示 token 表
3. 点 **语法分析** → 右侧「语法分析」页显示语法树
4. 点 **运行**（F5）→ 控制台输出 introduces 摘要、asserts/implies 逐条结论与整份规格判决

样例文件：

| 文件 | 覆盖的语法点 |
|---|---|

| `InsertGenerated.lsl` | 只有签名与 `generated by`、没有等式的最小 trait |
| `Bag2.lsl` | 集合字面量 `{ }`、三参数算子 `rangeCount`、单行 implies 量化声明 |

## 四、架构

```
源码 .lsl
   │  Lexer        compiler.lexer    → List<Token> + List<LexError>
   ▼
Token 流
   │  Parser       compiler.parser   → Ast.Trait 列表 + List<ParseError>
   ▼
AST
   │  EquationChecker compiler.runtime → List<CheckResult>
   ▼
控制台 / 错误列表 / 语法树 / token 表   （compiler.CompilerFrame）
```

| 包 | 职责 |
|---|---|
| `compiler` | `CompilerFrame` 主窗口；`ExcuteProgram`/`OpenFile` 为旧版遗留 |
| `compiler.lexer` | `Lexer`、`Token`、`TokenType`、`LexError`、`LexResult` |
| `compiler.parser` | `Parser`、`Ast`、`TreePrinter`、`ParseError`、`ParseResult` |
| `compiler.runtime` | `Evaluator`、`Domains`、`Value`、`EquationChecker`、`CheckResult` |
| `util` | 编辑器与界面组件（`StyleEditor`、`JFileTree`、`JStatusBar` 等） |
| `exceptions` | 自定义异常 |

## 五、支持的 LSL 子集

```
trait       := IDENT [ '(' params ')' ] ':' 'trait' clause*
clause      := 'introduces' signature*
             | 'asserts' genClause? partClause? varDecl? equation*
             | 'includes' ref (',' ref)*
             | 'assumes' ref (',' ref)*
             | 'implies' (ref (',' ref)* | varDecl equation*)
             | 'converts' ref (',' ref)*
             | 'exempting' varDecl? expr (',' expr)*
signature   := opName ':' [ sort (',' sort)* ] '→' sort
opName      := (IDENT | NUMBER | OPERATOR | ',')+        // 例：__ + __、0,1
genClause   := IDENT 'generated' 'by' ref (',' ref)*     // 例：C generated by empty, insert
partClause  := IDENT 'partitioned' 'by' ref (',' ref)*   // 例：C partitioned by isEmpty, head, tail
varDecl     := IDENT (',' IDENT)* ':' sort (',' IDENT (',' IDENT)* ':' sort)*
ref         := name [ '(' arg (',' arg)* ')' ]           // arg 可为 IDENT/运算符，或 "A for B" 重命名
equation    := expr ['==' expr] ';'?
expr        := 'if' expr 'then' expr 'else' expr
             | expr '⇒' expr
             | expr '==' expr
             | expr '∨' expr
             | expr '∧' expr
             | expr ('='|'≠'|'∈'|'∉'|'<'|'>'|'<='|'>='|'≤'|'≥') expr
             | expr ('+'|'-'|'*'|'/') expr
             | '~' expr
             | IDENT '(' args ')' | IDENT | NUMBER | STRING | '(' expr ')' | '{' [expr (',' expr)*] '}'
```

- 关键字：`trait sort introduces operators includes asserts assumes implies generated by partitioned
  converts exempting for using applied when if then else new add lookup belong`
- 注释：`--` 或 `//` 到行尾
- 运算符：`== = ≠ ~ ∈ ∉ ∧ ∨ ⇒ ⇔ ≤ ≥ → + - * / < > <= >=`，以及任意用户自定义中缀算子
- 标识符支持中文

## 六、运行时模型（等式检查）

LSL 是声明式规格，没有执行语义。「运行」的含义是**验证规格内部是否自洽**，按三层语义进行：

| 段 | 含义 | 检查什么 |
|---|---|---|
| `introduces` | 算子签名 | 只列出（`名字/元数`），不参与验证 |
| `asserts` | 算子的等式**定义** | 定义是否自洽：每条等式在各取值下是否成立 |
| `implies` | 由 asserts 推得的**性质** | 推论是否成立：asserts 的解释能否支撑该结论 |
| `converts` | 唯一确定取值的算子 | 只列出 |

检查方式是在变量排序的取值域上**枚举**、逐组代入两条边比较：

| 排序 | 取值域 | 对应实现 |
|---|---|---|
| `Int` / `Ind` / `Val` / `E` | 0、1、2 | 整数 |
| `Bool` | false、true | 布尔 |
| `Tab` | 4 个映射实例 | `new` / `add` / `lookup` / `size` / `isEmpty` |
| `C` / `Q` / `Container` / `B` / `Bag` / `Str` | 5 个序列实例 | `empty` / `insert`（有序插入）/ `head` / `tail` / `count` / `rangeCount` / `∈` / `∉` / `{ }` 字面量 |

每条等式/推论给出三种结论：

- **通过**：所有有定义的取值下两边相等（附「跳过 N 个未定义取值」）
- **失败**：给出第一个反例（变量取值 + 左右计算结果）
- **无法求值**：未实现的算子或未知排序

整份规格给出三种判决：

| 判决 | 条件 |
|---|---|
| **规格自洽** | asserts 与 implies 全部通过 |
| **规格矛盾** | 任一处出现反例（定义自相矛盾，或推论不被定义支持） |
| **部分无法验证** | 存在无法求值的部分 |

另有**结构检查（introduces ↔ asserts）**，不做求值，只核对声明与定义是否对应：每个在 `introduces` 中声明的算子，
是否在 `asserts` 里被定义（定义 = 等式左侧的根算子，或被 `generated by` / `partitioned by` / `converts` 覆盖）。
声明了却没有定义的算子会以警告列出；算子形参（如 `P(+, E)` 中的 +）与字面量签名（如 `0,1`）不参与检查。

关于「未定义」：`head(empty)`、`tail(empty)` 返回 ⊥。LSL 不要求术语无定义时等式成立，因此这些取值**被跳过**
而不是判为失败或无法求值。`⇒`、`∧`、`∨` 做短路求值，避免 `~isEmpty(c) ⇒ count(head(c), c) > 0` 这类
守卫式推论在 `c = empty` 时被误报。

> 例 1：Container 的 6 条定义等式全部通过（第 6 条跳过 9 个空序列取值），`~isEmpty(c) ⇒ count(head(c), c) > 0`
> 推论通过，判决为「规格自洽」。把 `count(e, empty) == 0` 改成 `== 1`，判决立即变为「规格矛盾」。
>
> 例 2：PQueue 的 `head(insert(e, q))` / `tail(insert(e, q))` 两条定义通过，推论 `e ∈ q ⇒ e ≥ head(q)`
> 通过，判决为「规格自洽」。模型中的 `insert` 采用**有序插入**——Container 不约束顺序，PQueue 要求
> `head` 为最小元素，有序插入同时满足两者；若改成普通头插，PQueue 的两条定义立即出现反例。

## 八、已知限制

- **界面视觉细节未人工确认**：已有窗口级自动化测试（`UiSmokeTest`，需图形环境，无显示时自动跳过），覆盖编辑、撤销、复制粘贴、词法/语法/运行、缩放、标签页切换；配色与间距仍需人工目视
- **等式检查是有限枚举**：不是定理证明，取值域之外的输入不覆盖；`Tab`/序列模型只是参考实现
- **泛型 trait 无模型**：以运算符为形参的 trait 需要实例化后才能数值验证，单独给出时只能做结构检查
- **语法高亮未启用**：`CodeStyle` 的关键字表仍被注释
- **旧代码并存**：`util` 中的旧解析类未删除，避免破坏 `test` 包
